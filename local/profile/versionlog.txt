2026052645:
    - Eixo auto-progression hardening (no behaviour change in the common
      all-visible case):
        * Hidden Eixo no longer breaks progression. The completed Eixo is now
          located against the FULL ordered list (visible + hidden), so a
          completion that lands while an Eixo is temporarily hidden (admin
          editing it) still resolves its position instead of silently
          stalling forever (the course_completed event is idempotent and
          never re-fires). Enrolment still targets only the next VISIBLE
          (reachable) Eixo.
        * Transient enrol failures now retry. When the next Eixo is found, the
          user isn't enrolled yet, and local_profile_auto_enrol_in_course()
          reports failure, a bounded adhoc task (local_profile\task\
          enrol_next_eixo) is queued: up to 3 attempts with 5min/30min/2h
          backoff. It is scoped to the specific freshly-completed pair (NOT a
          history sweep), so it can never resurrect enrolments an admin
          removed on purpose, and it is idempotent via is_enrolled().
        * The bulk backfill (Recalcular/upgrade) passes queueretry=false so it
          never floods the adhoc queue — admins re-run it manually instead.

2026052605:
    - Eixo auto-progression now works on courses that use enrol_self
      (or any other enrolment plugin) — not only enrol_manual.
        * The previous enrolment helper hardcoded plugin='manual' and
          required exactly one active manual instance per course. In
          production the Eixos commonly disable manual and rely on
          enrol_self so students can join from the top-navigation Eixos
          menu (which links to /enrol/index.php). The strict check
          meant every system-initiated enrolment failed silently:
            - First Eixo on profile save: not enroled.
            - Next Eixo after completing the current one: not enroled.
              Symptom: "menu shows Eixo 3 liberado but the student is
              never actually enroled, only manually self-enroling
              works."
            - Mass enrolment in non-Eixo courses: silently incomplete.
        * New helper local_profile_auto_enrol_in_course() picks the
          enrolment plugin from the course's enabled instances in this
          order: manual → self → first other enabled (cohort, lti, …),
          skipping plugins that aren't safe for unattended use (guest,
          paypal, stripe, fee). Each attempt is wrapped in try/catch
          so a plugin-level failure falls through to the next.
        * enrol_self_plugin::enrol_user() honours the underlying
          enrol_plugin contract: calling it programmatically just
          writes user_enrolments, the password/key gate lives in
          /enrol/index.php and is correctly bypassed for an admin-
          initiated progression.
        * Three callers updated to use the permissive helper:
            - local_profile_enrol_in_first_eixo
            - local_profile_enrol_in_next_eixo
            - local_profile_enrol_in_all_non_specialization_courses
          local_profile_enrol_user() stays as-is (still strict, still
          manual-by-default) so callers that intentionally want the
          old behaviour keep it.
    - db/upgrade.php step 2026052605 re-runs
      local_profile_backfill_eixo_progression() so production sites
      whose 2026052604 backfill silently failed (Eixos using enrol_self)
      finally get their students enroled in the next Eixo. The backfill
      is idempotent — sites whose 2026052604 pass already worked just
      see a 0-row pass this time.

2026052604:
    - One-shot backfill for the Eixo auto-progression.
        * Production sites that ran pre-2026052602 (the version that
          wired \local_studypace\event\course_completed into
          local_profile_enrol_in_next_eixo) have an existing population
          of students with completed Eixos whose event never had a
          listener — studypace::mark_course_completed() short-circuits
          and fires the event ONLY on the first write of
          local_studypace.actualcompletion, so post-deploy nothing
          retriggers for them. Symptom: "student finished Eixo 1 long
          ago, after the upgrade still wasn't auto-enrolled in Eixo 2".
        * New db/upgrade.php step iterates every (user, course-Eixo)
          completion already on disk and pushes each through the
          idempotent local_profile_enrol_in_next_eixo(). Already-enrolled
          users and non-Eixo completions (e.g. Sala de Conferências)
          are no-ops, so the upgrade is safe to re-run.
        * Re-firing the studypace event was intentionally avoided —
          that would also re-emit planned_completion(_high_grade),
          double-counting badges and re-sending achievement messages.
        * New helper local_profile_backfill_eixo_progression() in lib.php
          backs the upgrade and is also callable from CLI scripts /
          adhoc tasks if a site ever needs to replay the catch-up.

2026052603:
    - Performance + robustness sweep on the enrolment helpers:
        * local_profile_enrol_in_all_non_specialization_courses() no
          longer issues one is_enrolled() (context + enrolment) query
          per candidate course. It now pulls the user's existing
          enrolments in a single enrol_get_users_courses() call and
          pushes the "not an Eixo" filter into a NOT IN clause, so the
          remaining work is a small in-memory diff plus one enrolment
          per course that actually needs it. On a site with hundreds
          of non-Eixo courses this turns a first profile save from
          "noticeably slow" to "imperceptible".
        * local_profile_enrol_user() previously returned false on three
          soft-failure paths (enrol plugin disabled, plugin missing,
          wrong number of enrolment instances on the course) without
          any signal. The auto-progression observer just swallowed the
          false, so a misconfigured Eixo manifested as "students never
          advance" with no log to look at. The function now calls
          debugging() with a precise message on each false path so the
          admin sees it in Site administration → Development → Debug
          messages when debugging is on.
    - Observer::course_completed exception handler switched from
      error_log() (lands in php-error.log / Apache log, invisible to
      the Moodle UI) to debugging(DEBUG_NORMAL) so failures surface in
      the standard Moodle debug stream.
